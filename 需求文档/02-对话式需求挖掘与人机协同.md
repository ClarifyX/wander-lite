# 对话式需求挖掘与人机协同

## 设计原则

用户需求是模糊的。产品不能把模糊当成「信息不足请填表」。Agent 要像本地朋友一样挖隐性偏好，但追问必须克制。

- 一次最多 **2 个问题**
- 能从用户原话里抽到的槽位不要再问
- 核心槽位不齐时 **禁止输出路线 JSON**
- 槽位齐了之后，回复里必须包含 **一个 JSON 代码块**（见 `08-数据协议.md`）
- 语气短、具体、口语，不要问卷腔，不要客服腔

## 槽位（Slots）

按优先级收集。标了「核心」的全部有值才允许生成。

| 槽位 | 核心 | 说明 | 合法值示例 |
| --- | --- | --- | --- |
| city | 是 | 城市 | 上海、北京、杭州，或其他明确城市 |
| mode | 是 | 出行方式 | `walk` 老街区漫步 / `cycling` 城市骑行 / `trail` 公园轻越野 |
| durationHours | 是 | 时长（小时） | 1 / 1.5 / 2 / 3，范围 1～3 |
| startArea | 是 | 起点片区或「家附近」 | 杨浦、五道口、西湖边、不确定 |
| vibe | 否 | 风格氛围 | 安静、烟火气、工业遗存、林荫、滨水 |
| avoidTouristy | 否 | 默认 true | 避开网红打卡 |
| coffee | 否 | 是否中途停咖啡/甜品 | 要 / 不要 / 随意 |
| terrain | 否 | 路面 | 尽量平、可以有缓坡、轻越野土路 OK |

缺省策略：

- `avoidTouristy` 未提则视为 true
- `coffee` 未提则视为 随意
- `startArea` 用户说「随便 / 你定」可记为「由路线自定起点」，算已填

## 对话状态机

```
idle
  → 用户首条消息
mining          追问、补槽。一次 ≤ 2 问。不输出路线 JSON。
ready_to_generate 核心槽位齐，前端把「请根据槽位输出 JSON」作为下一轮约束发给模型
preview         前端已解析出合法 JSON，展示路线卡片 +【确认】【重新生成】
                此时地图仍保持原状（空，或仍显示上一条已确认路线）
confirmed       用户点确认，才调用地图渲染
rejected        用户点重新生成，或在输入框说「太长了 / 更安静」
                → 带着反馈回到 mining 或直接再 generate
error           JSON 抽不出或校验失败，向用户说明，允许重试
```

前端必须自己维护这套状态，不要指望模型守纪律。模型即使提前吐了 JSON，未到 `ready_to_generate` 也应忽略，或仅当核心槽位已齐时采纳。

## Agent 人设（写入 DeepSeek system 消息）

你是「轻漫游」里的本地向导，只做城市周边 1～3 小时微漫游：老街区步行、城市骑行、公园轻越野。

规则：

1. 先抽取用户已给的槽位，只问还缺的核心槽位，每次最多 2 问。
2. 禁止规划跨城、多日、机票酒店。若用户要长途，明确拒绝并拉回短途。
3. 避开过曝点：外滩、田子坊、豫园人潮、西湖断桥/雷峰塔、南锣鼓巷、宽窄巷子等。给「同类氛围的非网红替代」。
4. 地点必须是真实存在的公共空间 / 街道 / 公园 / 滨江 / 可查到的咖啡馆。不许编造店名。没有把握的点不要写进 JSON。
5. 点位 4～8 个，顺序可走通，总时长匹配。给 WGS84 经纬度，精确到小数点后 4～6 位。
6. 核心槽位齐之前：只聊天，不要输出 JSON。
7. 核心槽位齐之后：先用 2～4 句中文说明这条路为什么适合对方，然后输出 **唯一一个** 形如 \`\`\`json ... \`\`\` 的代码块，结构严格符合协议。代码块外不要再塞第二个 JSON。
8. 用户要求修改时，在上一轮路线上改，不要装失忆。

## 人机分工

| 交给 AI | 交给人 |
| --- | --- |
| 从自然语言抽槽位 | 确认「我就从杨浦出发」这种生活事实 |
| 克制追问 | 决定走不走这条路 |
| 编排点位、顺序、短介绍 | 点【确认】或【重新生成】 |
| 输出地图可用 JSON | 用一句话改约束（更安静 / 缩短 / 加点咖啡） |

闸门放在「有合法 JSON 初稿之后」。

- 再往前（每问都要点确认）会把对话做成表单。
- 再往后（模型一返回就画图）幻觉成本不可接受。

## 前端在对话里要做的事（不是模型的事）

1. 解析模型回复：先展示自然语言部分；若有 JSON 代码块再尝试 parse。
2. parse 失败：进入 `error`，提示「路线数据解析失败，点重新生成或再说一次偏好」，**不渲染地图**。
3. parse 成功：进入 `preview`，在聊天区渲染路线预览卡（店名列表、时长、距离），显示两个按钮。
4. 【确认】：`confirmed`，调用地图 API 打点画线，fitBounds。
5. 【重新生成】：把「请换一条，保持已收集偏好，避开上一轮点位」发给模型。
6. 用户在预览态继续打字：视为修改意见，带上当前 JSON 摘要再请求。

## 开场白（页面加载后助手自动说一句）

「跟我说一句你隐约想去的方向就行。比如：周末下午在市区骑两小时，想看老厂房，避开网红点。我一次最多问两个问题，问清了再给你一条可走的短途。」

## 示例对话（实现时用这个做手工测试脚本）

用户：周末想骑车，别太累，看看老房子。

助手：可以。你在哪座城市、大概从哪个片区出发？这次想骑多久，1 小时还是 2 小时左右？

用户：上海，杨浦附近，2 小时。

助手：（简述）+ \`\`\`json ... \`\`\`

前端：预览卡 + 确认 / 重新生成。

用户点确认 → 地图出现点与线。
